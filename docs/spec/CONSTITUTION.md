## 项目行为准则（Karpathy 四大核心原则）

### 1️⃣ Think Before Coding（三思而后行）

> **原则**: "Don't assume. Don't hide confusion. Surface tradeoffs."

| 要求 | 说明 | 禁止 |
|-----|------|------|
| 明确陈述假设 | 如果不确定，主动提问 | ❌ 假设用户意图 |
| 呈现多种解释 | 不要默默选择一个方案 | ❌ 默默做决定 |
| 提出更简单的方法 | 适当时候推回 | ❌ 不提反对意见 |
| 遇到不清楚就停止 | 说出哪里不清楚并提问 | ❌ 盲目继续 |

**触发场景**:
- 用户需求不明确时 → 先问清楚再实现
- 存在多种实现方案时 → 呈现权衡让用户选择
- 发现假设可能错误时 → 立即表面并验证

### 2️⃣ Simplicity First（简单优先）

> **原则**: "Minimum code that solves the problem. Nothing speculative."

| 要求 | 禁止 |
|-----|------|
| 无单次使用的抽象 | ❌ 过度设计类继承 |
| 无"灵活性"或"可配置性" | ❌ speculative features |
| 无未来可能用到的代码 | ❌ "以后可能会用"的代码 |
| 无不相关代码的"改进" | ❌ 顺手改别的地方 |

**触发场景**:
- 实现前先问："这个抽象真的需要吗？"
- 看到"为以后预留"的代码 → 删除
- 看到过度设计的类结构 → 简化为简单函数

### 3️⃣ Surgical Changes（精准修改）

> **原则**: "Touch only what's needed."

| 要求 | 说明 |
|-----|------|
| 只改直接相关的行 | 不要"改善"周围的代码 |
| 保持风格一致 | 遵循项目的风格指南 |
| 模仿现有模式 | 与项目现有代码保持一致 |
| 不要溢出修改 | 改 A 功能时不碰 B 功能 |

**红线**:
```
❌ 改了一个函数，顺便改了其他3个函数
❌ 修复bug时，同时做了代码重构
❌ 改了配置，顺便改了不相关的常量
```

### 4️⃣ Goal-Driven Execution（目标驱动执行）

> **原则**: "Define success criteria and loop until verified."

| 要求 | 说明 |
|-----|------|
| 定义成功标准 | 明确什么是"完成" |
| 设定验证检查点 | 每个阶段都有验证点 |
| 迭代直到验证通过 | 不满足就继续调整 |
| 使用可验证的目标 | "添加验证" → "为无效输入写测试" |

**验证检查点机制**:
```
阶段 1: 需求理解 → 用户确认 ✓
    ↓
阶段 2: 方案设计 → 评审通过 ✓
    ↓
阶段 3: 代码实现 → 自测通过 ✓
    ↓
阶段 4: 集成测试 → 测试通过 ✓
```

## 不可协商项

### 2.1 行为准则不可协商项（Karpathy 原则）

| 项目 | 要求 | 说明 | 溯源 |
|------|------|------|------|
| Think Before Coding | 明确假设、问清楚、不隐藏困惑 | 需求不明确时必须先澄清 | Karpathy |
| Simplicity First | 最小代码、无 speculative features | 禁止过度抽象和预留代码 | Karpathy |
| Surgical Changes | 只改必要的、不改无关的 | 禁止溢出修改 | Karpathy |
| Goal-Driven | 定义成功标准、验证检查点 | 禁止跳过验证 | Karpathy |

### 2.3 技术不可协商项
| 项目 | 要求 | 说明 | 溯源 |
|------|------|------|------|
| 技术栈 | Java 21 + Spring Boot 3 | 必须使用指定版本 | |
| 代码规范 | 遵循 Modern Java 规范 | 必须使用 Record、Optional 等现代特性 | |
| 安全标准 | 符合 OWASP Top 10 安全要求 | 必须进行安全审查 | |
| 测试要求 | 单元测试覆盖率 > 80% | 必须达到指定覆盖率 | |

### 2.4 业务不可协商项
| 项目 | 要求 | 说明 | 溯源 |
|------|------|------|------|
| 功能范围 | 必须包含核心功能 | 明确核心功能边界 | |
| 性能指标 | 响应时间 < 200ms | 必须达到性能要求 | |
| 合规要求 | 符合 GDPR 数据保护 | 必须遵守数据保护法规 | |

### 2.5 流程不可协商项
| 项目 | 要求 | 说明 | 溯源 |
|------|------|------|------|
| 开发流程 | 必须遵循规范驱动开发 | 先设计后开发 | |
| 代码审查 | 必须进行代码审查 | 所有代码变更必须审查 | |
| 测试流程 | 必须执行集成测试 | 使用 Testcontainers | |

## 3. 决策框架

### 3.1 技术决策流程
1. **提案**: 提出技术方案和理由
2. **评估**: 多角色评估技术可行性
3. **决策**: 基于评估结果做出决策
4. **记录**: 记录决策过程和结果

### 3.2 业务决策流程
1. **需求分析**: 分析业务需求和影响
2. **方案设计**: 设计多个解决方案
3. **方案评估**: 评估各方案的利弊
4. **决策执行**: 执行决策并跟踪结果

## 4. 治理机制

### 4.1 角色与职责
| 角色 | 职责 | 权限 |
|------|------|------|
| 架构师 | 技术架构设计和审查 | 技术决策审批 |
| 产品经理 | 需求定义和产品规划 | 需求变更审批 |
| 测试专家 | 测试策略和质量保障 | 质量门禁审批 |
| 开发者 | 代码实现和单元测试 | 代码提交权限 |

### 4.2 变更管理
- **变更类型**: 重大变更、一般变更、微小变更
- **变更流程**: 变更申请 → 影响评估 → 审批 → 实施 → 验证
- **变更记录**: 所有变更必须记录在案
