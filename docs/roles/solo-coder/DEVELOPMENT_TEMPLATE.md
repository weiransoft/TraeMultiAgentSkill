# 独立开发模板

## Karpathy 四大核心原则（行为准则）

> **来源**: Andrej Karpathy 对 LLM 编程常见陷阱的观察
> **目的**: 减少 LLM 编程中的错误、过度复杂、无关修改等问题

### ⚠️ LLM 常见问题（The Problems）

| 问题类型 | 具体表现 |
|---------|---------|
| **错误假设** | 模型代替用户做出错误假设，不检查就执行 |
| **管理混乱** | 不管理自己的困惑，不寻求澄清 |
| **不一致** | 不表面不一致，不提出权衡方案 |
| **不反馈** | 应该推回时不推回 |
| **过度复杂** | 喜欢把代码和 API 过度复杂化 |
| **无关修改** | 改一处代码时溢出到不相关的区域 |

### 1️⃣ Think Before Coding（三思而后行）

**原则**: "Don't assume. Don't hide confusion. Surface tradeoffs."

**独立开发者应用场景**:

| 场景 | 应用原则 | 具体行为 |
|------|---------|---------|
| 理解需求时 | 明确陈述假设 | 明确输入格式、数据来源、边界条件 |
| 设计方案时 | 呈现多种解释 | 提供简单/复杂方案及其权衡 |
| 发现问题时 | 停止并提问 | 说清楚哪里不清楚，不要盲目猜测 |
| 假设可能错误时 | 立即验证 | 验证假设后再继续 |

**示例**:
```
用户: "添加一个导出用户数据的功能"

❌ 错误做法（隐藏假设）:
def export_users(format='json'):
    # 假设用户只需要导出所有用户
    # 假设 JSON 是唯一需要的格式
    ...

✅ 正确做法（明确假设）:
"""
需要确认：
1. 是导出所有用户还是特定条件的用户？
2. 需要哪些字段？（全部还是部分）
3. 格式除了 JSON 还需要其他吗？（CSV、Excel等）
"""
```

### 2️⃣ Simplicity First（简单优先）

**原则**: "Minimum code that solves the problem. Nothing speculative."

**独立开发者红线**:

| 禁止 | 示例 | 正确做法 |
|------|------|---------|
| ❌ 单次使用的抽象 | 为了一次调用创建类 | 直接写函数 |
| ❌ speculative features | "以后可能需要"的可配置项 | 只实现当前需要的 |
| ❌ 过度设计 | 简单工具类用继承模式 | 简单的函数调用 |
| ❌ 预留代码 | 为未来功能写占位符 | 只写必要的代码 |

**触发检查**:
```
实现前问自己：
1. 这个抽象真的需要吗？→ 可能不需要
2. 这个参数真的需要可配置吗？→ 硬编码可能更简单
3. 这个函数以后会被复用吗？→ 不确定就不要抽象
```

### 3️⃣ Surgical Changes（精准修改）

**原则**: "Touch only what's needed."

**独立开发者红线**:

| 禁止 | 示例 | 正确做法 |
|------|------|---------|
| ❌ 溢出修改 | 修复bug时改了其他3个函数 | 只改必要的行 |
| ❌ 顺便重构 | 修复bug时顺便优化代码 | 单独的refactor提交 |
| ❌ 格式化修改 | 改代码时顺便格式化 | 单独的format提交 |
| ❌ 改注释 | 不相关的注释修改 | 不要碰注释 |

**修改前检查**:
```
git diff 查看修改：
1. 每一行修改都是必要的吗？
2. 有没有顺手改的其他函数？
3. 有没有格式化带来的变更？
```

### 4️⃣ Goal-Driven Execution（目标驱动执行）

**原则**: "Define success criteria and loop until verified."

**验证检查点**:

```
阶段 1: 需求理解 → 用户确认 ✓
    ↓
阶段 2: 方案设计 → 自己评审 ✓
    ↓
阶段 3: 代码实现 → 单元测试通过 ✓
    ↓
阶段 4: 集成测试 → 测试通过 ✓
```

**成功标准定义示例**:
```
用户: "实现用户登录功能"

定义成功标准：
1. ✅ 用户输入正确账号密码能登录成功
2. ✅ 用户输入错误密码登录失败并提示
3. ✅ 用户输入不存在账号登录失败并提示
4. ✅ 连续5次登录失败账号锁定15分钟
5. ✅ 单元测试覆盖率 > 80%
```

**验证驱动开发示例**:
```
❌ 错误做法:
"添加验证" → 直接写代码 → 完成

✅ 正确做法:
"添加验证" → "为无效输入写测试" → "让测试通过" → 验证完成
```
