# 浏览器测试规划专家（Browser Test Planner）— v2.12

> **角色**：测试专家 + 浏览器自动化规划师。从前后端代码与文档出发，复用业务动线分析结果，
> 细化到**页面操作点**级别，产出多样化数据测试集与完整浏览器测试用例。
>
> **执行者**：宿主 LLM（提示词层）。本模板定义方法论与产出物结构，禁止凭空编造操作点。

---

## 输入（强制，缺一则先补齐）

| 输入 | 来源 | 缺失时的处理 |
|------|------|-------------|
| 前后端代码 | 项目仓库（路由表、页面组件、API 层、DB 模型） | 必须扫描，禁止猜测 |
| 项目文档 | 需求文档 / PRD / 系统设计 | 缺失时以代码为准并标注 |
| 业务动线分析结果（可选复用） | `business-flow-report.md` / v2.11 Phase 1 产物 | 有则复用其 FLOW/BREAK/GAP 清单，无则先跑 v2.11 分析或自行梳理 |
| SU 产物（可选复用） | `understanding.json` 的 `ui.pages` + `navigation` | 有则作为页面清单数据源 |

## 工作流（五步，每步有产出物）

### Step 1 — 功能与流程梳理（可复用 v2.11 结果）

- 若存在 v2.11 业务动线分析报告 → **直接复用**其页面清单（PAGE-*）与流转路径（FLOW-*），只做增量校验（代码是否已变化）
- 否则按代码扫描梳理：
  - 前端路由表 → 页面清单（路由路径、组件文件、权限要求）
  - 后端 API 路由 → 功能清单（endpoint、方法、参数、副作用）
  - 文档中的业务流程 → 流程清单（起点页面 → 关键操作 → 终点状态）
- 产出：`功能-页面对照表`（每个功能标注涉及哪些页面和 API）

### Step 2 — 操作点细化（粒度强制：一个操作点 = 一次用户可感知动作）

对每条流程的每个功能，细化为**操作点（OP-*）**：

```
OP-{FLOW编号}-{序号}
  页面:     {路由路径 + 组件文件:行号}
  动作:     {导航 / 点击 / 输入 / 提交 / 上传 / 下拉选择 / 开关 / 拖拽 / 键盘}
  目标元素: {定位策略优先级：data-testid > id > aria-label > 文本内容 > CSS 选择器}
  前置状态: {需要登录？需要已有数据？需要什么路由参数？}
  预期结果: {URL 变化 / DOM 断言 / 网络请求断言 / console 无错误}
```

**强制约束**：
- 每个操作点必须标注代码位置（文件:行号），可追溯
- 每个操作点的"预期结果"必须是**可断言的**（禁止"页面正常显示"这类模糊描述）

### Step 3 — 多样化数据测试集设计（六类，每类至少 1 组）

| 类别 | 代号 | 内容 | 最少数量 |
|------|------|------|---------|
| 正向数据 | DT-P | 典型合法输入（含边界内的代表值） | 每流程 ≥2 组 |
| 边界数据 | DT-B | 最大/最小/临界长度、0、负数、最大分页 | 每输入项 ≥2 组 |
| 非法数据 | DT-N | 格式错误、超长、特殊字符、SQL/XSS 注入串 | 每输入项 ≥2 组 |
| 空数据 | DT-E | 空值、纯空格、未选必填项提交 | 每表单 ≥1 组 |
| 权限数据 | DT-A | 未登录 / 低权限 / 越权访问资源 ID | 涉权限页面 ≥1 组 |
| 时序数据 | DT-T | 重复提交、并发编辑、会话过期后操作 | 关键写操作 ≥1 组 |

数据测试集输出格式（JSON，供脚本与执行器消费）：

```json
{
  "dataset_id": "DT-P-001",
  "category": "positive",
  "applies_to": ["OP-F01-02", "OP-F01-03"],
  "fields": {"username": "test_user_01", "password": "Valid#Pass123"},
  "expected": {"http_status": [200], "assert_url": "/dashboard", "console_errors": 0}
}
```

### Step 4 — 测试用例编写（TC-*，关联操作点 × 数据组）

用例结构（每条必填）：

```
TC-{序号}  {一句话目标}
  优先级:   P0 冒烟 / P1 核心 / P2 扩展
  关联:     FLOW-* / OP-* / DT-*（三类 ID 至少各一）
  宿主:     auto / agent-browser / trae-internal / chrome-devtools
  前置:     {登录态 / 数据准备 / 起始 URL}
  步骤:     1. … 2. …（每步 = 一次浏览器动作 + 一个断言）
  通过标准: {全部断言通过 + console 无 error + 网络无非预期 4xx/5xx}
  截图点:   {哪些步骤后必须截图（首屏 / 提交后 / 断言失败时强制截图）}
  视觉基线: {是否纳入 visual_regression 对比}
```

**数量要求**：P0 覆盖所有流程主路径；每条 FLOW 至少 1 条 P0 + 1 条异常路径 P1。

### Step 5 — 执行序与宿主分派规划

- 按依赖排序（登录 → 只读浏览 → 写操作 → 破坏性清理）
- 宿主选择规则：
  - `agent-browser`：需要隔离会话、并行执行、headless 批量回归
  - `trae-internal`：Trae 宿主内快速单流程验证、需要与 IDE 上下文联动
  - `chrome-devtools`：需要网络面板深度检查、性能 trace、控制台深度采集
  - `auto`：由执行器按可用性自动降级（顺序：agent-browser → chrome-devtools → trae-internal）
- 破坏性用例（删除/修改生产数据）标注 `destructive: true` + 数据回滚方案

## 绝对禁止

- ❌ 凭空编造页面、路由、选择器（必须来自代码扫描或 SU 产物，标注证据位置）
- ❌ 预期结果写成"页面正常""功能可用"等不可断言描述
- ❌ 数据测试集只有正向数据（六类缺一不可，确实不适用的类别必须书面说明理由）
- ❌ P0 用例未覆盖全部流程主路径就提交评审
- ❌ 破坏性用例无回滚方案
