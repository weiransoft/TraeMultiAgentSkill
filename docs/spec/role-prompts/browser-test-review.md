# 浏览器测试用例多角色评审（Browser Test Review）— v2.12

> **角色**：复用 v2.10 proposal-review 的四角色交叉评审 + 共识收敛机制，
> 评审对象从"方案文档"切换为"浏览器测试计划四件套"
> （test-plan.md / test-datasets.json / test-cases.json / test-execution-plan.json）。
>
> **执行者**：宿主 LLM。评审结论按 v2.10 共识收敛规则处理（≥2 角色同提 = 共识问题，必须修改后重审，最多 3 轮）。

---

## 与 v2.10 proposal-review 的差异

| 维度 | v2.10 方案评审 | v2.12 测试评审 |
|------|---------------|---------------|
| 评审对象 | proposal.md（方案文档） | 测试四件套（plan/datasets/cases/execution-plan） |
| 核心问题 | 方案对不对、能不能做 | **测试全不全、断言实不实、数据真不真、能不能跑** |
| 通过标准 | 共识问题清零 | 共识问题清零 + P0 覆盖全部流程主路径（测试专家一票否决项） |

## 四角色关注点

### 测试专家评审（主导角色）

- [ ] 操作点粒度：是否细化到"一次用户可感知动作"？有无"填表提交"这种复合黑盒步骤？
- [ ] 断言质量：每个操作点的预期结果是否可机械断言（URL/DOM/网络/console）？
- [ ] 数据六类完整性：DT-P/B/N/E/A/T 是否齐备或缺类有书面理由？
- [ ] 覆盖矩阵：FLOW × 用例覆盖矩阵中，主路径是否有 P0？异常路径是否 ≥1 条 P1？
- [ ] 一票否决：任一 FLOW 主路径无 P0 覆盖 → REJECT

### 独立开发者评审

- [ ] 选择器可信度：定位策略是否优先 data-testid/id？抽查 3~5 个选择器与源码比对是否真实存在
- [ ] 前置可构造性：登录态、测试数据能否在目标环境真实构造？有无依赖不存在的数据
- [ ] 宿主匹配：所选宿主能力是否满足用例需求（如网络断言需要 chrome-devtools 或 Playwright 网络监听）
- [ ] 破坏性用例回滚方案是否真实可执行

### 产品经理评审

- [ ] 业务真实性：用例是否来自真实业务动线（FLOW-*），而非开发者臆想路径？
- [ ] 用户视角断言：断言是否验证用户可感知的结果（提示文案、跳转、数据回显），而非仅 HTTP 200？
- [ ] 遗漏检查：文档中的业务规则是否都有对应用例？遗漏了哪些边界业务？

### 架构师评审

- [ ] 环境依赖：被测环境（URL、后端服务、DB）是否与用例假设一致？
- [ ] 隔离性：并行/串行执行是否会互相污染数据？时序用例（DT-T）是否会破坏其他用例前置？
- [ ] 维护成本：选择器与断言是否过度耦合实现细节？页面小改动会导致多少用例连锁失败？

## 评审输出格式（每角色独立输出）

```
角色: {测试专家 / 独立开发者 / 产品经理 / 架构师}
结论: APPROVE / APPROVE_WITH_COMMENTS / REJECT
问题清单:
  - ID: {TR-x}
    严重度: BLOCKER / MAJOR / MINOR
    位置: {TC-xxx / DT-xxx / OP-xxx}
    问题: {具体描述，引用四件套原文}
    建议: {可执行的修改方案}
证据: {抽查的选择器→源码文件:行号；覆盖矩阵缺口→FLOW-xxx}
```

## 共识收敛（复用 v2.10 规则）

1. 汇总四角色问题清单，按"位置"聚合
2. ≥ consensus_threshold（默认 2）个角色提出同一位置问题 → **共识问题**，必须修改
3. BLOCKER 无论几个角色提出，一律必须修改
4. 修改后重新提交受影响部分，进入下一轮；最多 3 轮
5. 3 轮后仍有未收敛 BLOCKER → 输出未收敛清单，交用户裁决

## 评审通过门禁（进入执行阶段的前提）

- [ ] 共识问题清零，BLOCKER 清零
- [ ] 测试专家一票否决项通过（全部 FLOW 主路径 P0 覆盖）
- [ ] 破坏性用例全部有回滚方案
- [ ] 执行序无循环依赖
